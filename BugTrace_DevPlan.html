1　计划总览

1.1　编制依据

本计划基于《BugTrace MVP 范围定义 V0.1》，将 14 个功能点、8 张数据表、3 个角色拆解为 5 个阶段（P0–P4），每个阶段有独立交付物与验收门槛，阶段之间存在显式依赖。计划只描述「做什么、改哪里、怎么验、谁确认」，不含代码。

1.2　阶段全景

W1 前半P0 基础准备环境 + 数据层 + 骨架 · 4 人日

W2 前半P2 用例与计划用例 + 计划 + 关联 · 3 人日
W2 中段P3 Bug 流转Bug 闭环核心 · 4 人日

1.3　人力与工期

  • 团队配置：前端 1 人（Vue + Element Plus）、后端 1 人（NestJS + Prisma）
  • 工期：2 周（10 工作日），含 1.5 人日缓冲
  • 并行策略：P0 完成后，前端与后端在 P1–P3 阶段并行——后端先出接口 + Swagger Mock，前端基于 Mock 开发，每日联调
  • 关键路径：P0 → P1 → P2 → P3 → P4，任一阶段延期都会压缩后续缓冲

0
P0　基础准备
环境就绪 · 8 表落库 · 前后端骨架可跑通
工期 4 人日依赖 无角色 全员
阶段目标

搭好开发环境、把 8 张表落库、前后端骨架能跑通「登录页 → 空首页」一条链路。本阶段不写业务功能，只铺路。

涉及功能
  • 无业务功能。本阶段交付的是基础设施，对应 MVP 功能清单的「前置条件」
预期修改范围
层改动项产出物
环境Docker Compose（app + postgres 两容器）、Node 22 + NestJS CLI、Vue 3 + Vite 脚手架docker-compose.yml、可启动的空项目
数据层Prisma Schema 定义 8 张表 + 枚举 + 外键 + 索引；首次 migrationschema.prisma、迁移文件
后端骨架NestJS 项目结构（modules/controllers/services）、全局异常过滤器、JWT 鉴权中间件、Swagger 配置、统一响应拦截器可启动的 NestJS 服务 + /docs 接口文档页
前端骨架Vue Router 路由表（含 3 角色菜单）、Pinia store、Axios 封装、Element Plus 引入、登录页 + 空布局可访问的登录页 + 登录后空首页
约定接口风格、错误码、分页、命名规范文档化（写在 README）README.md
验收标准
  1. Docker Compose 一键启动，两个容器健康
  2. Prisma 迁移成功，数据库出现 8 张表，字段与 MVP 文档 2.2 节一致
  3. 后端服务启动后访问 /docs 能看到空 Swagger 文档（无业务接口，只有健康检查）
  4. 前端启动后能看到登录页，输入任意凭据能调到后端接口（即使返回 401）
  5. 前后端跨域配置正确，无 CORS 报错
  6. README 中写明启动命令、数据库连接、默认端口
⚠ 人工确认节点 G0-1：数据模型评审
  • 确认内容：8 张表的字段、类型、外键、索引是否与 MVP 范围一致
  • 确认人：技术负责人（后端开发本人或评审者）
  • 确认时机：Prisma Schema 写完、迁移执行前
  • 不确认的后果：表结构一旦落库并被业务代码引用，后续改字段成本陡增

P1　账户与项目
3 角色可登录 · 项目可创建 · 需求可登记
工期 3 人日依赖 P0角色 全员
阶段目标

实现登录鉴权与项目/需求的基础 CRUD，让 3 个角色能登录并进入各自视角。这是后续所有业务功能的前置——没有项目就没有归属，没有登录就没有操作人。

数据层无新表。初始化 user 表的种子数据（3 个角色各 1 个账号）seed.ts
后端auth 模块（登录/登出/JWT 签发）、project 模块（CRUD + 成员邀请）、requirement 模块（CRUD）、全局 Guard（从 JWT 解析用户）5 个接口 + Swagger 文档
前端登录页对接真实接口、token 存储、路由守卫（未登录跳登录页）、项目列表页、项目创建弹窗、需求列表页、需求创建表单、3 角色菜单差异化4 个页面 + 2 个弹窗

  2. ADMIN 登录后能创建项目、邀请成员（指定角色）、登记需求
  3. DEV / QA 登录后看不到「创建项目」「登记需求」入口（菜单差异化生效）
  4. 未登录访问任意业务页面自动跳转登录页
  5. Swagger 文档中出现本阶段 5 个接口且可调试
⚠ 人工确认节点 G1-1：角色权限验证
  • 确认内容：3 个角色登录后看到的菜单与可执行操作是否符合 MVP 权限矩阵
  • 确认人：产品 / 技术负责人
  • 确认时机：P1 开发完成、P2 开始前
  • 不确认的后果：权限模型错了，后面所有功能都会基于错误前提开发

P3　Bug 流转（核心）
Bug 从提单到关闭全链路闭环
工期 4 人日依赖 P2（◐ 可降级）角色 全员
阶段目标

实现 MVP 的核心闭环：Bug 提单 → 分派 → 修复 → 回归 → 关闭。这是 90 分钟演示的主线，也是 14 个功能点中权重最高的部分。本阶段完成后，MVP 的业务价值已经成立。

#功能优先级主角色
7用例关联 BugP0QA
8Bug 提单P0QA / 全部
9Bug 列表与筛选P0全部

预期修改范围
层改动项产出物
数据层无新表。使用 bug / bug_log / attachment 表—
后端bug 模块（提单/列表/详情/状态流转/分派/修复说明/回归）、attachment 模块（上传/下载）、bug-log 自动记录逻辑（每次状态变更追加流水）10 个接口
前端Bug 列表页（筛选：状态/严重度/处理人）、Bug 提单表单（含截图上传）、Bug 详情页（含状态流转按钮 + 修复说明表单 + 操作流水时间轴 + 关联用例选择器）2 个页面 + 2 个表单
状态机6 状态流转校验：新建→已分派→处理中→已修复→已验证→已关闭 + 重开分支 + 拒绝分支bug-status.machine.ts
权限分派仅 QA、修复说明仅 DEV、回归验证仅 QA、拒绝仅 ADMINpermission.const.ts 扩展
文件存储本地 uploads 目录 + 静态文件托管nginx 配置 / NestJS StaticModule
验收标准
  1. QA 能提交 Bug，18 个字段全部可填，截图能上传并预览缩略图
  2. Bug 列表支持按状态、严重度、处理人筛选，分页正常
  3. QA 能将 Bug 分派给 DEV，状态从「新建」变「已分派」，bug_log 记录一条
  4. DEV 登录后列表只显示分派给自己的 Bug
  5. DEV 能将状态改为「处理中」并填写修复说明（根因/方案/影响），状态变「已修复」
  6. QA 能执行回归验证，通过则状态变「已验证」→「已关闭」，失败则重开回「处理中」
  7. 每个状态变更都在 bug_log 留下操作人、时间、前后状态、备注
  8. 非法流转被拦截（如「新建」直接跳「已关闭」返回 400）

降级预案：若 P2 延期导致 P3 时间不足，可先实现「Bug 不关联用例」的简化版（功能点 7 后置到 P4），保证核心流转闭环。关联用例在 P4 联调时补回。

⚠ 人工确认节点 G3-1：状态机走查
  • 确认内容：6 状态流转规则、非法流转拦截、bug_log 记录完整性
  • 确认人：产品 / QA 代表
  • 确认时机：P3 开发完成、P4 开始前
  • 不确认的后果：状态机是 MVP 核心，错了演示必翻车
⚠ 人工确认节点 G3-2：权限边界验证
  • 确认内容：分派仅 QA、修复仅 DEV、回归仅 QA、拒绝仅 ADMIN，越权操作被拦截
  • 确认人：技术负责人
  • 确认时机：P3 开发完成、P4 开始前
  • 不确认的后果：演示时角色切换可能暴露越权问题
