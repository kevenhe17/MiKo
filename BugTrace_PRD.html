2项目背景与目标

2.1 现状与痛点

在多平台、多版本并行交付的研发体系中（典型如 Android 板卡 / 固件类项目，涉及多芯片平台、多机型、多基线并行），质量协同普遍存在以下六大痛点：

痛点 01 · 测试准备
用例靠人肉堆，覆盖靠经验

PRD 与用例脱节，边界 / 异常 / 权限 / 兼容场景易遗漏；用例散落在 Excel、脑图、文档里，无法复用与沉淀。

痛点 02 · Bug 反馈
Bug 描述不可复现

「点了几下就崩了」式描述普遍，缺少环境、版本、账号、前置条件、步骤、日志截图，研发反复追问，单均沟通成本高。

痛点 03 · 研发定位
缺少上下文，靠猜

Bug 与需求、代码变更、日志、接口信息割裂在不同系统，研发无法快速拿到复现路径与影响面，容易在证据不足时下结论。

痛点 04 · 修复验证
回归范围拍脑袋

修复后没有系统化回归清单，只验证「原来那一步」，导致修复引入新问题、Bug 反复重开。

痛点 05 · 版本验收
上线决策缺数据

验收靠口头与群聊拼信息，未解决 Bug、阻塞项、延期风险没有统一视图，上线风险难以量化。

痛点 06 · 分支变更
主干/分支流向黑盒

代码从 feature 到 release 到 trunk 的流向、合入门禁状态、哪些改动进了哪个版本，全靠人问；热修复忘记回流主干，同一 Bug 在下一版本复发。

第 6 个痛点是本次新增模块的核心动因 变更流向不可视会直接导致三类事故：① 漏合（修复只进了发布分支，没回流主干）；② 错合（把未测试完成的特性带进了发布分支）；③ 回滚困难（出问题时无法快速定位「这一版到底进了哪些改动」）。因此本 PRD 将「主干 / 分支软件变更流转界面」作为一等公民模块进行设计。

2.2 产品定位

一体化 Web 协同平台，打通「需求 / PRD — 测试用例 — Bug — 代码变更 — 分支合入 — 版本发布 — 质量复盘」的数据链路，让质量过程可记录、可流转、可追溯、可量化。

维度定位说明
产品形态Web 端（B/S）为主，移动端仅提供只读看板与消息处理（P2）
部署方式支持 SaaS 与私有化部署；支持与 GitLab / GitHub / Gitee、Jenkins、企业 IM 集成
核心差异① 六阶段质量闭环一体化；② 主干/分支变更流转可视化 + 可配置门禁；③ 提交级双向追溯（版本 → 提交 → 变更单 → Bug/需求 → 用例）
不做的事不替代代码仓库与 CI 系统本身；不做 IDE 插件（V1.0）；不做自动化测试执行引擎（仅接入与结果回传）

2.3 目标与成功指标

业务目标

  1. 提效：将「提单—定位—修复—验证—关闭」的平均流转时长降低 30%。
  2. 提质：将缺陷逃逸率（线上缺陷 / 总缺陷）控制在 5% 以内。
  3. 可控：让每一次进入主干与发布分支的变更都「有单、有审、有测、有门禁、可回滚」。
  4. 可沉淀：把复盘结论转化为测试规范与研发检查清单，形成组织资产。

关键指标（上线后 3 个月对比基线）

缺陷平均修复时长 MTTR↓ 30%
一次修复通过率（30 天内未重开）≥ 85%
缺陷逃逸率（线上/总）≤ 5%
回归自动化覆盖率≥ 60%
变更导致线上事故数↓ 40%
热修复漏回流主干事件0 起
版本验收报告准备耗时↓ 50%
Bug 单字段完整率≥ 90%

术语英文 / 缩写定义
主干Trunk / Main代码仓库的主分支，始终保持「可发布」状态；仅接受发布分支与热修复分支的合入
发布分支Release Branch从主干切出用于版本冻结与缺陷收敛的分支，命名 release/vX.Y.Z，仅接受 bugfix 类变更
特性分支Feature Branch需求开发分支，命名 feature/<需求号>-<简述>，短生命周期，合入后删除
缺陷修复分支Bugfix Branch命名 bugfix/<Bug号>-<简述>，可指向主干、发布分支或热修复分支
热修复分支Hotfix Branch从线上版本 Tag 切出，用于紧急修复，修复后必须双向回流（主干 + 当前发布分支）
变更单Change Request（CR）本平台核心对象：一次「代码 / 配置 / 脚本 / 产物」变更的正式载体，承载分支流向、门禁状态、审批与追溯

缺失提交Missing Commit存在于 A 分支但未合入 B 分支的提交，系统需支持检测与一键 Cherry-pick 建议
测试用例Test Case（TC）最小可执行验证单元，含前置条件、步骤、预期结果、优先级与类型
测试计划Test Plan（TP）面向某版本/迭代的测试范围、环境、排期、负责人与准入准出标准的集合
测试执行单Test Run测试计划的一次实例化执行，记录每个用例的执行人与结果
回归清单Regression Suite（RS）由 Bug 修复说明自动生成（或人工调整）的回归用例集合
严重度Severity（S1–S4）Bug 对系统造成的客观危害程度，由测试 / 质量判定
优先级Priority（P0–P3）Bug 被修复的紧急程度，由产品 / 研发负责人判定
阻断上线Release Blocker未解决则不允许版本发布的 Bug 或风险项
缺陷逃逸Defect Escape测试阶段未发现、发布后被用户发现的缺陷
重开率Reopen Rate验证不通过或关闭后再次打开的 Bug 占比

  • 权限可继承可覆盖：项目级角色为默认，版本级与分支级可单独授予（例如「发布分支 release/v2.1 的合入权限」）。
  • 关键动作双人原则：生产主干合入、强制放行、紧急回滚建议开启「申请人 + 审批人非同一人」校验。
  • 全量留痕：所有写操作写入审计日志，包含操作人、时间、来源 IP、变更前/后值。

9接口与集成需求

9.1 内部接口规范

  • 风格：RESTful over HTTPS，JSON 编码，版本前缀 /api/v1/；时间字段统一 ISO 8601（UTC），金额与比率使用字符串避免精度丢失。
  • 鉴权：Bearer Token（JWT）+ 项目级 Scope；写操作需携带 Idempotency-Key 防重复提交。
  • 分页：统一 page / pageSize（默认 20，上限 200），返回 total 与 hasMore。
  • 错误码：HTTP 状态码 + 业务码（{code, message, traceId, details[]}）；4xx 需给出可操作的修复建议。
  • 幂等与并发：状态流转接口使用乐观锁（version 字段），冲突返回 409 并附最新状态。
