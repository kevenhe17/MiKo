如何使用本清单

本文档把开发计划 P0–P4 五个阶段拆为 24 个 Codex 可执行任务。每个任务为一个独立增量：一次只喂给 Codex 一个任务，验收通过后再喂下一个。任务之间按「建议执行顺序」串联，顺序号即全局拓扑序；带 人工确认 的任务完成后必须暂停，等人工确认通过再继续。

2　P0 基础准备（6 个任务 · 4 人日）

本阶段不写业务功能，只铺路：环境、数据、骨架。6 个任务全部为后续阶段的地基，按 T0-1 → T0-6 顺序执行，其中 T0-2 完成后必须等待 G0-1 人工评审，通过后才能执行 T0-3 迁移。

T0-1

Docker Compose 环境搭建

P0 · 基础准备 无需人工确认
Goal

本地一条命令启动 postgres + app 两个容器，数据库对宿主机可连接。

Context

MVP 硬约束为「Docker Compose 单机部署，不上 K8s」。所有后续任务（迁移、接口、联调）都依赖数据库容器先起来。app 容器此时只承担 npm run start:dev 占位，业务代码后续填充。

Constraints
  • 仅 2 个容器：postgres:16 + app（node:22 镜像）；不引入 redis / minio / nginx。
  • 端口约定：postgres 5432、app 3000，统一写入 .env，禁止硬编码。
  • postgres 数据目录挂载命名卷，容器重建不丢数据；两容器加 healthcheck。
  • 产出物：docker-compose.yml、.env、.env.example。
Acceptance Criteria
  • docker compose up -d 后 docker compose ps 显示两容器 healthy。
  • 宿主机用任意客户端（psql / DBeaver）以 .env 中的账号密码可连接 5432。
  • app 容器内可解析并连通 postgres 主机名。
  • README 中记录启动/停止/看日志三条命令。
人工确认

否 — 用 AC 自动验收即可。

建议执行顺序

全局第 1 步（P0 内第 1 个，无前置）。

T0-2

Prisma Schema 定义（8 表 3 枚举）

P0 · 基础准备 需人工确认 G0-1
Goal

产出与《MVP 文档》2.2 节逐字对齐的 schema.prisma：8 张表 + 3 个枚举，只写不执行。

Context

Schema 是全项目唯一数据契约，所有业务代码依赖它。MVP 已冻结 8 表：user / project / requirement / test_case / bug / attachment / bug_log / test_plan。开发计划风险 #1（改表成本高）的防线就是本任务的 G0-1 评审。注意：迁移执行必须等 G0-1 通过，本任务只交付 schema 文件。

Constraints
  • 表与字段与 MVP 2.2 节逐项一致：bug 表 18 字段含 root_cause / fix_desc / impact 三件套；test_plan 用 case_ids Json 列存用例数组，不建关联表。
  • 3 个枚举：Role（ADMIN/DEV/QA）、BugStatus（NEW/ASSIGNED/IN_PROGRESS/FIXED/VERIFIED/CLOSED）、BugSeverity（BLOCKER/CRITICAL/MAJOR/MINOR）。
  • 主键 BigInt @id @default(autoincrement())；每表 created_at / updated_at @default(now())；外键字段一律建索引 @@index。
  • 命名：模型用驼峰、表名/列名下划线并 @map；不添加 deleted_at / version 等 V0.2 字段（MVP 明确延后）。
  • project 表按开发计划 P1「成员邀请」需要，预置 members Json 列（MVP 无 project_member 表，邀请即写入该列）。
Acceptance Criteria
  • npx prisma validate 零错误。
  • 8 个 model + 3 个 enum，数量与 MVP 2.2 一致；字段名与 MVP 表 2-2 逐列核对无遗漏、无多列。
  • 所有外键（project_id / requirement_id / owner_id / bug_id 等）均建索引。
  • 未执行 migrate —— schema 仅以文件形式提交。
人工确认

是 → 节点 G0-1（数据模型评审）：技术负责人逐字段核对类型/外键/索引与 MVP 一致后才允许进入 T0-3。确认结果在任务系统留痕。

建议执行顺序

全局第 2 步。前置 T0-1；其后必须暂停等待 G0-1。

T0-4

NestJS 骨架（异常 / 响应 / Swagger）

P0 · 基础准备 无需人工确认
Goal

可启动的 NestJS 服务：统一响应格式、全局异常过滤器、Swagger、健康检查。本任务不写任何业务接口。

Context

技术栈已冻结（NestJS 10 + Prisma）。骨架是所有业务模块（auth/project/requirement/test-case/test-plan/bug/attachment）的底座。开发计划风险 #5（接口契约不一致）的预防手段之一是后端先出 Swagger——本任务先把 Swagger 页立起来。

Constraints
  • 目录规范：src/modules/{auth,project,requirement,test-case,test-plan,bug,attachment} 先建空壳 module。
  • 统一响应 { code, message, data }，成功 code=0；全局异常过滤器把 HttpException 转成统一格式，业务错误码从 HttpStatus 派生。
  • Swagger 挂 /docs，页面标题「BugTrace API」。
  • 仅提供 GET /health 健康检查（返回 { status: 'ok', db: 'up' }，含数据库 ping）。
Acceptance Criteria
  • npm run start:dev 无报错，监听 3000。
  • 访问 /health 返回 200 且 JSON 为统一响应格式；数据库断开时 db 字段变 down。
  • 访问 /docs 看到 Swagger 页（此时仅 health 一个接口）。
  • 请求一个不存在的路由，返回统一错误格式 { code: 404, message, data: null }。

T0-5

JWT 鉴权基础接线

P0 · 基础准备 无需人工确认
Goal

全局 AuthGuard 就位：无 token / 伪造 token 一律 401，白名单（/health、/docs、后续 /auth/*）放行。

Context

登录业务在 P1（T1-1）才实现，本任务只做「守门」基础设施：JwtModule 配置 + 全局 Guard + 放行白名单。这样 P1 写登录接口时鉴权链路已通，避免 P1 一次性堆太多代码。

Constraints
  • JWT 密钥从 .env 读取（JWT_SECRET），签名算法 HS256，有效期 8h。
  • Guard 全局注册（APP_GUARD），白名单用装饰器/常量表维护：/health、/docs*、/auth/login。
  • 本任务不解析用户信息（@CurrentUser 注入留到 T1-1），只验证 token 存在性与签名。
  • 401 响应必须走 T0-4 的统一错误格式。
Acceptance Criteria
  • 无 token 访问任意业务路由 → 401 统一错误。
  • 伪造 token（篡改签名）→ 401；过期 token → 401。
  • /health、/docs 匿名可访问（不弹 401）。
人工确认

否。

建议执行顺序

全局第 5 步。前置 T0-4。

T0-6

Vue3 前端骨架（路由 / Pinia / Axios）

P0 · 基础准备 无需人工确认
Goal

可访问的登录页 + 登录后空布局，3 角色菜单占位渲染；Axios 封装与 401 拦截就绪。

Context

技术栈冻结：Vue 3 + Vite + Element Plus + Pinia + Vue Router。登录页先静态，T1-4 再对接真实接口。骨架把「页面怎么组织、请求怎么发、状态怎么存」的约定固化，后续每个页面任务只写页面本身。

Constraints
  • 路由表：/login + 布局路由（子路由 /projects /requirements /cases /plans /bugs 占位页）。
  • Pinia 建 user store（token + user 信息，先空壳）；Axios 实例 baseURL 指向 VITE_API_BASE，请求拦截器自动带 Authorization: Bearer，响应拦截器遇 401 跳 /login。
  • Element Plus 全量引入（MVP 不做按需加载）；菜单组件按 role 渲染三套占位（数据写死，T1-5 接真实）。
  • 不写任何业务逻辑；登录按钮点击发出请求（允许 401）。
Acceptance Criteria
  • npm run dev 打开即见登录页，样式正常。
  • 输入任意值点登录会向 /auth/login 发请求（即使返回 401）。
  • 登录后进入空首页布局；手动改 localStorage 塞 token 可跳过登录（MVP 不做守卫强校验，T1-4 补）。
  • 三个占位菜单结构存在且按角色互不相同。

否。

T1-1

种子账号 + auth 模块

P1 · 账户与项目 无需人工确认
Goal

3 个角色种子账号可登录并拿到 JWT；提供登录/登出接口。

Context

T0-5 已把 Guard 白名单留好 /auth/login。本任务补齐认证闭环：seed.ts 写入 admin/dev/qa 三个账号（bcrypt 加密密码），auth 模块签发 JWT。这是「谁是操作人」的起点，后续所有接口的 @CurrentUser 注入依赖它。

Constraints
  • 种子账号：admin / dev / qa，密码统一初始值 123456，role 对应 ADMIN/DEV/QA；seed 幂等（upsert）。
  • 密码用 bcrypt 加密存储，禁止明文。
  • POST /auth/login 返回 { token, user }；POST /auth/logout 仅做成功响应（MVP 无服务端 session，前端清 token）。
  • MVP 不做注册、改密、刷新 token；JWT payload 含 sub + role。
  • 实现 @CurrentUser() 参数装饰器（从 Guard 解析后的 token 注入用户）。
Acceptance Criteria
  • 3 个账号均可登录拿到 token，token 可解出正确 role。
  • 错误密码 → 401 统一错误；不存在的账号 → 401。
  • Swagger 中 /auth/login 可调试，返回结构符合统一响应。
  • 带 token 访问一个占位业务接口，@CurrentUser 能取到用户。
人工确认

否。

T1-4

前端登录对接（token + 路由守卫）

P1 · 账户与项目 无需人工确认
Goal

登录页走真实接口；token 持久化；未登录访问业务页跳转 /login；退出登录。

Context

T0-6 的静态登录页与 T1-1 的登录接口都已就绪，本任务把两端接通——这是「前后端首次联调」，会暴露 Axios 封装、CORS、统一响应解包的第一批问题，务必在 P1 解决而不是拖到 P4。

Constraints
  • token 存 localStorage（MVP 简化，不做 cookie）；刷新后从 localStorage 恢复并回填 Pinia。
  • 路由守卫：无 token 访问业务路由 → redirect /login；已登录访问 /login → redirect 首页。
  • 登录失败（401/网络错误）在表单上给出可读提示；登录成功跳转 /projects。
  • 响应拦截器统一解包 { code, message, data }：code≠0 抛业务错误；401 清 token 跳登录。
Acceptance Criteria
  • admin/dev/qa 三账号均可登录进入首页；错误密码显示提示且不跳转。
  • 刷新页面登录态保持；退出后回 /login 且 localStorage 无 token。
  • 未登录直接访问 /projects → 自动跳 /login。
  • 后端接口返回 401 时前端全局拦截并跳登录（不白屏）。
人工确认

否。

T1-5

项目 / 需求页面 + 3 角色菜单

T3-1

Bug 状态机 + 提单 / 列表 / 详情接口

P3 · Bug 流转 无需人工确认
Goal

落地集中式状态机定义；实现 Bug 提单、列表筛选、详情三个查询类接口。

Context

状态机是 P3 的锚——所有流转接口（T3-2）都走它校验，UI 按钮（T3-6）也由它推导。MVP 状态机：6 状态 + 重开 + 拒绝。开发计划风险 #3（流转遗漏边界）的防线：本任务先写流转矩阵，再写接口。

Constraints
  • bug-status.machine.ts 集中定义：状态枚举、TRANSITIONS 合法流转表（key: from, value: 合法 to 数组）、每步动作的权限角色（assign→QA/ADMIN、start/fix→DEV、verify→QA/ADMIN、reject→ADMIN、reopen→QA/ADMIN）。
  • 流转表必须覆盖：NEW→ASSIGNED→IN_PROGRESS→FIXED→VERIFIED→CLOSED；重开 FIXED→IN_PROGRESS；拒绝 ASSIGNED→CLOSED（经 reject 动作）。NEW→CLOSED 等跳步非法。
  • 接口：POST /bugs（18 字段，code 自动生成 BUG-{项目code}-{4位序号}）、GET /bugs（筛选 status/severity/owner_id + 分页）、GET /bugs/:id（含 bug_log 列表 + attachment 列表）。
  • DEV 的列表：仅返回 owner_id 或 fixer_id 为自己 的 Bug（服务层过滤，不是前端过滤）。
  • 提单校验必填：project_id/title/severity/module/environment/steps/expected/actual。
Acceptance Criteria
  • 状态机文件有单元测试：每个 from 的合法 to 集合与拒绝集合断言通过。
  • 提单成功返回 code；缺必填字段 → 400。
  • 列表三筛选组合 + 分页正常；DEV 视角只见自己的 Bug。
  • 详情返回完整字段 + 空 bug_log + 空 attachment 数组（结构已就位）。

T3-2

Bug 流转接口 + bug_log 自动留痕

P3 · Bug 流转 无需人工确认
Goal

Context

T3-1 的状态机与提单接口就绪。本任务把「流转动作」做全——每个动作接口内先过状态机校验、再写状态、再写流水，三步在同一个事务里完成。bug_log 是「每步留痕」演示的核心证据。

Constraints
  • 接口与权限：POST /bugs/:id/assign（QA/ADMIN，body: ownerId + comment）、/start（DEV，自动置 fixer_id=自己）、/fix（DEV，body 必填 root_cause/fix_desc/impact 三件套）、/verify（QA/ADMIN，body: passed: bool + comment）、/close（QA/ADMIN）、/reopen（QA/ADMIN，body: comment）、/reject（ADMIN，body: reason）。

Acceptance Criteria
  • 从 NEW 到 CLOSED 的完整链路每个动作都能走通，bug_log 逐条追加（数量 = 动作次数）。
  • DEV 调 /assign → 403；QA 调 /fix → 403；DEV 调 /reject → 403；ADMIN 调 /verify 合法。
  • NEW 状态直接调 /close → 400；修复三件套缺任一 → 400。
  • 回归失败路径：FIXED→verify(false)→IN_PROGRESS，流水含两条（verify + reopen）。
  • 流转矩阵单元测试覆盖 T3-1 定义的每个合法/非法路径。

7.2　执行纪律（防止 Codex 跑偏）

  • 一次一个任务：24 个任务按顺序号逐个提交，禁止把多个任务塞进一次对话——每个任务都是独立可验收的增量，混在一起无法定位回归。
  • 验收先行：Codex 完成代码后，必须让它自己跑 AC 中的验证（单元测试 / curl / 页面操作），并在回复中贴证据；AC 不过不进入下一步。
  • 禁止越界：任务卡片 Constraints 中「不引入 / 不做 / 延后」的项（如不接 MinIO、不做软删除）是硬边界，Codex 若自作主张实现，直接打回。
  • 状态机是唯一真相：P3 起所有 Bug 流转行为（含前端按钮显隐）一律从 bug-status.machine.ts 推导，发现 UI 与状态机不一致时改状态机，禁止在组件里另写 if 分支绕过。
  • 提交频率：每个任务至少一次提交，提交信息含任务号（如 T3-2: 流转接口+留痕），便于按任务回滚。
  • 失败即停：单个任务连续失败或卡住超过预期时，停止并带着报错回人工，不要自行扩大改动范围。
