1　目标与约束

1.1　演示目标

用 90 分钟向团队完整演示一次 Bug 从发现到关闭的全流程，证明「数据结构清晰、功能闭环、可继续扩展」三件事。演示结束即可决定是否进入 V0.2 开发。

1.2　硬约束

#约束说明
190 分钟内可演示完毕含环境准备 10 分钟 + 演示 60 分钟 + 答疑 20 分钟。功能超出时间预算的一律砍到 V0.2
2无复杂权限3 角色（ADMIN/DEV/QA），权限点硬编码，不做角色配置页、不做权限矩阵 UI
3无复杂统计不做仪表盘、不做趋势图、不做报表。只做「Bug 列表 + 状态筛选」
4无复杂流程Bug 状态机 6 个状态、CR 不做状态机只做记录、不做门禁、不做分支、不做合入
5数据结构清晰8 张表，外键关系明确，字段命名规范，为 V0.2 扩展留接口
6功能闭环从「建项目 → 提 Bug → 修复 → 回归 → 关闭」一条链路走通，不中断
7后续可扩展数据模型兼容 PRD V1.0 的 17 张表，V0.2 加字段不改表结构

1.3　验收标准

  1. 3 个角色（ADMIN/DEV/QA）均可登录并看到各自视角的页面
  2. ADMIN 能创建项目、邀请成员、登记需求
  3. QA 能提 Bug、分派给 DEV、执行回归、关闭 Bug
  4. DEV 能看到分派给自己的 Bug、填写修复说明、标记已修复
  5. Bug 状态在 6 个状态间正确流转，每步留操作记录
  6. Bug 列表支持按状态、严重度、处理人筛选
  7. 演示脚本（5.2）可完整走完不报错

2.2　数据模型（8 张表）

砍掉 PRD V1.0 的 9 张表，只留驱动 Bug 闭环的最小集合。所有表都用 BigInt 主键、created_at / updated_at 时间戳。

表 2-2　MVP 数据模型（8 张表，覆盖 14 个功能点）
#表名关键字段用途
1userid, username, password_hash, realname, role(全局), created_at系统用户。MVP 用全局 role 简化，V0.2 改为 project_member
2projectid, code, name, description, created_by, created_at项目。MVP 不做 repo_url / gate_config 等集成字段
3requirementid, project_id, code, title, description, status, created_at需求。只做登记，不做 PRD 解析、不做版本关联
4test_caseid, project_id, module, title, precond, steps, expected, priority, created_at测试用例。MVP 不做版本基线、不做快照
5bugid, project_id, code, title, severity, priority, status, module, environment, steps, expected, actual, owner_id, fixer_id, root_cause, fix_desc, impact, requirement_id, case_id, created_atBug 主表。18 个字段，含修复说明三件套（根因/方案/影响）
6attachmentid, project_id, target_type, target_id, filename, filepath, size, uploaded_by, created_at附件。target_type 区分 bug / case，filepath 指本地路径
7bug_logid, bug_id, operator_id, action, from_status, to_status, comment, created_atBug 操作流水。每次状态变更追加一条，只增不改
8test_planid, project_id, name, owner_id, case_ids(JSON), status, created_at测试计划。case_ids 用 JSON 数组存，不做关联表

为什么是 8 张而不是更少：再砍就会破坏闭环——去掉 bug_log 就无法演示「每步留痕」；去掉 attachment 就无法演示「截图复现」；去掉 test_plan 就无法演示「测试准备」。这 8 张是闭环的最小必要集。

为 V0.2 预留的扩展点（已在表结构中留好）：

  • bug 表的 root_cause / fix_desc / impact 三字段，V0.2 改为 JSONB 即可承载更复杂的定位证据结构
  • test_plan 的 case_ids JSON，V0.2 可无痛迁移为 test_plan_case 关联表
  • user 表的全局 role，V0.2 拆为 project_member 表后，老数据按 role 直接迁移
  • 所有表都没有 deleted_at，V0.2 加软删除字段不影响现有逻辑

4　后续再做什么

4.1　V0.2 近期补强（演示通过后 2–3 周）

V0.2 的目标是「让 MVP 能真正用起来」，补齐演示版缺失的运营能力。

#功能价值
1项目级角色（project_member 表）同一人在不同项目可不同角色
2站内信 + 企微机器人Bug 分派 / 状态变更实时通知
3仪表盘（Bug 分布 + 趋势）QA 看概况不用翻列表
4Bug 搜索（标题 + 全文）列表多了之后必须
5审计日志表（audit_log）记录合入 / 放行等关键动作
6软删除（deleted_at）误删可恢复
7附件迁移到 MinIO为多实例部署做准备

4.2　V1.0 正式版（V0.2 之后 8–10 周）

V1.0 对齐 PRD 与技术方案 V1.0 的完整范围，MVP 数据结构可直接升级。

#模块新增能力
1变更流转（CR）CR 状态机、门禁 G1–G6、分支冻结、合入、Waive
2GitLab 集成分支同步、MR 审批、Pipeline 状态、提交追溯
3版本管理版本基线、版本冻结、变更清单、Release Note
4回归测试套件CR 修复后自动生成回归清单
5质量复盘缺陷分布、根因分类、修复效率、遗留风险
6智能提醒（3 条）Bug 超时分派、阻断项变更、CR 卡点
7权限制衡互审回避、Waive 双人、全量审计

8

6　技术栈与交付

6.1　技术选型

MVP 沿用技术方案 V1.0 的选型，但做最小化裁剪——只留驱动 14 个功能点的依赖。

层选型说明
前端Vue 3 + TS + Vite + Element Plus表单 / 表格 / 步骤条开箱即用，不自研组件
后端Node 22 + NestJS 10 + PrismaSwagger 自动生成接口文档，Prisma 直接出 8 张表的 schema
数据库PostgreSQL 16单库，不接 Redis / MinIO
部署Docker Compose（2 容器）app + postgres，单机起
存储本地文件系统附件存 ./uploads，Nginx 托管

6.2　工程约定

  • 接口风格：RESTful，路径 /api/v1/...，统一返回 {code, msg, data}
  • 鉴权：JWT，登录返回 token，放 Header Authorization: Bearer xxx
  • 错误处理：全局异常过滤器，统一错误码（4xx 业务错误，5xx 系统错误）
  • 校验：class-validator + DTO 装饰器，前端 Element Plus 表单校验对齐
  • 时间：统一 UTC 存储，接口返回 ISO 8601 字符串，前端格式化
  • 分页：统一 page / pageSize，默认 20 条
  • 命名：表名蛇形（snake_case），字段蛇形，接口驼峰，TS 接口帕斯卡
