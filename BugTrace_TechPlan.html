3　技术选型详解

3.1 前端选型

关注点结论说明
框架Vue 3 选定PRD 中大量「表格 + 抽屉详情 + 步骤条 + 看板」的组合，正是 Element Plus 的强项。React 需额外引入 Ant Design + ProComponents 才能达到同等开发速度
UI 库Element Plus 选定el-table 虚拟滚动可扛万行用例；el-steps 直接对应 CR 步骤条；el-drawer 对应详情抽屉
拖拽看板vuedraggable 选定SortableJS 封装，约 30 行代码即可实现泳道拖拽；跨泳道拖拽 V1.0 禁用，复杂度直接减半
图表ECharts 选定V1.0 只用到柱状图、饼图、折线图 3 种，按需引入控制包体积
流程图 / 状态机静态 SVG 降级放弃 AntV X6 / LogicFlow。V1.0 的流程可视化需求（状态机、门禁流水线）全部是静态展示，用 SVG + Element 步骤条即可，省掉约 1 周学习与联调成本
富文本Markdown 编辑器 降级放弃 wangEditor / TipTap。Bug 描述、验收结论用 Markdown（md-editor-v3），够用且存储天然干净
全局搜索后端 ILIKE 查询 降级不引入 Elasticsearch。只搜 Bug 标题/编号 + CR 标题/编号，PG 的 pg_trgm 索引在 10 万级数据下完全够用

3.2 后端选型

关注点结论说明
运行时Node.js 22 LTS 选定与前端同语言；2 人小队可互相 review、互相补位；招聘/交接也简单
框架NestJS 10 选定Module / Controller / Service 三层清晰；内置 Guard（权限）、Interceptor（日志/响应封装）、Pipe（参数校验）、Schedule（定时任务）；@nestjs/swagger 自动生成接口文档，前端直接看 Swagger 联调
ORMPrisma 5 选定Schema 即数据字典；迁移文件可版本化、可回滚；复杂关联查询用 include 一把梭，比 MyBatis 写 XML 快很多
参数校验class-validator + Zod 选定DTO 即校验规则，同时被 Swagger 读取生成文档
认证自建账号 + JWT 选定Access Token 2h / Refresh Token 7d，存 Redis 白名单；预留 auth 模块接口，V1.1 接 LDAP/OAuth2 不改业务代码
异步任务BullMQ 选定承载：代码仓定时同步（15 min）、门禁状态轮询（1 min）、通知推送（实时）、超时规则扫描（每日 09:00 / 15:00）
文件存储MinIO + S3 SDK 选定前端走后端预签名 URL 直传，不占用 API 带宽

被否决的后端方案及原因

方案结论否决 / 备选理由
Spring Boot 3 + MyBatis-Plus备选 B企业规范友好、生态最强，但 CRUD 与接口文档维护成本高；若团队已有 Java 人力或需纳入公司 IT 规范，切此方案（替换映射见 3.5）。预计工期 +2 周
Python FastAPI备选 C开发最快、AI 能力接入方便（V2.0 若要做 AI 生成用例，FastAPI 是加分项）；但工程化约束弱，2 人以上协作易失控。1 人全栈 + 未来重 AI 时选它
Go Gin否决性能过剩，本平台是典型的 IO 密集型 CRUD + 状态机，Go 的开发效率劣势被放大
Serverless / 低代码否决状态机与门禁引擎需要复杂事务与定时任务，低代码表达困难，后期必然返工

5.2 统一关联模型

PRD 要求「需求 / Bug / 用例 / 回归 / 变更单 / 版本」之间双向可追溯。若两两建关联表需要 6 张以上，V1.0 用一张 entity_link 统一承载。

字段取值说明
src_type / dst_typeBUG / CASE / CR / REQ / PLAN / REGRESSION / VERSION被关联对象类型
link_typeRELATE / BLOCK / DUPLICATE / DERIVE / FIX关联语义：关联 / 阻塞 / 重复 / 派生 / 修复
唯一约束(src_type, src_id, dst_type, dst_id, link_type)防重复关联

查询方式：对象详情页的「关联实体」区块，只需一条 where (src_type=X and src_id=?) or (dst_type=X and dst_id=?) 即可查出全部双向关联，无需按类型写多套 join。link_type 上的索引保证查询性能。

并发与一致性约定

  • 乐观锁：bug / change_request 增加 version 整型列，更新时校验；冲突返回 409 并提示「数据已被他人修改，请刷新」——避免两人同时拖拽 CR 卡片造成状态错乱。
  • 状态流转事务：状态变更 + 门禁结果写入 + 审计日志 + 通知投递，在单个数据库事务内完成；通知投递失败不影响主流程（记录失败队列重试）。
  • Webhook 幂等：GitLab 重复推送同一 pipeline_id / commit_sha 时，以唯一键去重后直接返回 200。
  • 软删除：Bug、CR、用例均不做物理删除，用 deleted_at 标记，保留追溯链。

两处刻意的降级设计：

① 「合入冲突」不做状态——原 PRD 有「待合入 → 合入冲突 → 待合入」的往返。V1.0 改为在 CR 上放一个 conflict_files 标记（来自 GitLab 合入失败回调），卡片显示 ⛓ 徽标，修复后刷新即可。省掉一个状态 + 两条流转 + 一套 UI 状态样式。

② 「回滚」不做状态流转——原 PRD 有「已发布 → 已回滚」并自动生成回滚 CR。V1.0 改为：ADMIN 手动创建一个 type=Rollback 的普通 CR 走正常流程，原 CR 上标记 rolled_back=true。功能不丢，但省掉一条特殊的自动化路径。

核心设计：用「互审」替代「上级审批」。去掉 DEV_LEAD 之后，最大的问题是「谁来审」。V1.0 的答案是——不指定谁有资格审，只规定谁没资格审：CR 的创建人自己不能审。任何一名 DEV（或 ADMIN）都可以审批任意 CR，只要那不是他自己创建的。

这条规则比「DEV_LEAD 审批」更贴合小团队：小公司不一定有正式的技术负责人头衔，但「别让作者自己审自己」这条规矩到哪儿都成立，而且它不依赖任何组织架构——团队今天 3 个人、明年 8 个人，规则都不用改。

权限划分的两把尺子：

  • DEV 只做「提出」，ADMIN 做「放行」：DEV 能创建 CR、能审批别人的 CR，但不能合入受保护分支、不能冻结分支、不能打 Tag——从根上杜绝「任何一个研发都能直接改主干」。
  • QA 做「判定」，ADMIN 做「终审」：QA 负责跑回归、判门禁结果、发起 Waive 申请；放行与验收结论由 ADMIN 拍板。测试与决策分离，QA 不需要为「能不能上线」背锅。

3 角色的制衡设计（四条硬约束，写进代码、不可配置绕过）：

  • 自审回避：审批人必须 ≠ CR 创建人，且角色为 DEV 或 ADMIN。这是 3 角色模型下唯一的审批防线，不可关闭。若项目内只有 1 名 DEV（无法互审），需开启 solo_mode 由 ADMIN 兜底审批，但审计日志标红、并在质量报告中单列「单人自审」数量。
  • 合入与发布收敛到 ADMIN：DEV 无任何合入 / 冻结 / 打 Tag 权限，审批通过不等于可以合入。
  • Waive 双人：门禁放行必须由 QA 发起申请、ADMIN 终审，缺一不可，不允许同一人走完两步。
  • 全量审计：合入、Waive、分支冻结 / 解封、发布打 Tag、手动标记门禁通过 —— 全部写 audit_log，记录只增不改不删。

10.4　枚举定义与实现约定

角色枚举在前后端共享包中定义，权限判定收敛为纯函数，禁止在业务代码里散落角色判断（避免出现 if (role === 'DEV' || role === 'ADMIN') 这种散落逻辑）：

// packages/shared/src/enums/role.enum.ts
export enum ProjectRole {
  ADMIN = 'ADMIN',  // 管理员 / 技术负责人：系统配置 + 关键卡点终审
  DEV   = 'DEV',    // 研发：修复、提交、互审他人 CR
  QA    = 'QA',     // 测试：提单、回归、门禁判定
}

// ── 关键卡点：只有 ADMIN 能做 ──────────────────────
export const canMergeCR      = (m: Member) => m.role === ProjectRole.ADMIN;
export const canFreezeBranch = (m: Member) => m.role === ProjectRole.ADMIN;
export const canReleaseTag   = (m: Member) => m.role === ProjectRole.ADMIN;
export const canWaiveGate    = (m: Member) => m.role === ProjectRole.ADMIN;  // Waive 终审

// ── 评审：互审 —— 审批人只要不是 CR 创建人即可 ──────
export const canApproveCR = (m: Member, cr: ChangeRequest) =>
  (m.role === ProjectRole.DEV || m.role === ProjectRole.ADMIN) &&
  cr.ownerId !== m.userId;

// ── 单人项目兜底：无他人可互审时由 ADMIN 审批并标红 ──
export const canApproveCRSolo = (m: Member, cr: ChangeRequest, solo: boolean) =>
  solo && m.role === ProjectRole.ADMIN && cr.ownerId === m.userId;

对应的数据模型。project_member 表只有 role 一个权限字段，没有任何标记位；audit_log 新增的 self_review 用于记录「单人模式下的自审」：

enum ProjectRole { ADMIN DEV QA }

model ProjectMember {
  id        BigInt      @id @default(autoincrement())
  projectId BigInt      @map("project_id")
  userId    BigInt      @map("user_id")
  role      ProjectRole
  createdAt DateTime    @default(now()) @map("created_at")

  @@unique([projectId, userId])
  @@index([userId])
  @@map("project_member")
}

model AuditLog {                       // 高风险动作留痕，只增不改不删
  id         BigInt   @id @default(autoincrement())
  projectId  BigInt   @map("project_id")
  userId     BigInt   @map("user_id")
  action     String                            // MERGE | WAIVE | FREEZE | TAG | GATE_OVERRIDE
  targetType String   @map("target_type")
  targetId   BigInt   @map("target_id")
  before     Json?
  after      Json?
  selfReview Boolean  @default(false) @map("self_review")  // 单人模式自审标红
  ip         String?
  createdAt  DateTime @default(now()) @map("created_at")

  @@index([projectId, createdAt])
  @@map("audit_log")
}

关于「ADMIN 会不会成为瓶颈」：会，但这是小团队的真实写照——3–10 人的公司里，能决定「这段代码能不能进主干、这个版本能不能发」的人本来就是固定的那一两个。系统要做的不是消除这个瓶颈，而是让瓶颈可见：CR 待合入超 48h、待评审超 48h、门禁失败超 24h 都会触发提醒（见 7.8），卡在谁那里一目了然。建议把 ADMIN 给到 2 个人，互为备份。

关于「以后角色不够用怎么办」：3 类角色是 V1.0 的约束，不是永久限制。因为枚举只有一个、权限判定集中在 permission.const.ts，后续要加回 DEV_LEAD 或拆分 PM，改动量约 0.5 人日（加枚举值 + 补矩阵列 + 改判定函数）。反过来说，如果 V1.0 一上来就做 8 角色 + 可配置权限矩阵，光配置页与权限引擎就要多花 8–10 人日，且小团队根本用不上。
